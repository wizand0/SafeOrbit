# Обзор обновлений Firebase Realtime Database Rules для SafeOrbit

## Цель

Обновить правила безопасности Firebase Realtime Database для поддержки новой системы client-only pairing с использованием одноразовых pairing токенов.

## Основные изменения

### 1. Структура данных сервера

```
servers/$serverId
├── ownerUid: string (владелец сервера)
├── pairing
│   ├── tokenHash: string (SHA-256 хеш одноразового токена)
│   ├── expiresAt: number (время истечения токена)
│   └── consumed: boolean (флаг использования токена)
├── location: object (информация о местоположении)
└── app_notifications: object (зашифрованные уведомления)
```

### 2. Права доступа

#### Чтение данных сервера
- Владелец: полный доступ ко всем данным сервера
- Связанный клиент: доступ к местоположению и уведомлениям
- Другие пользователи: нет доступа

#### Запись данных сервера
- Владелец: запись местоположения, команд, обновление pairing информации
- Другие пользователи: нет доступа

### 3. Pairing система

#### Создание сервера
- Только владелец может установить `ownerUid`, `tokenHash`, `expiresAt`
- Поля `tokenHash` и `expiresAt` нельзя изменить после создания

#### Использование токена
- Токен может быть использован только один раз (через transaction)
- После использования устанавливается флаг `consumed = true`
- Нельзя изменить `consumed` обратно на `false`

### 4. Команды сервера

#### Отправка команд
- Клиенты могут отправлять команды в `server_commands/$serverId`
- Только связанные клиенты могут записывать команды
- Только владелец сервера может читать команды

#### Валидация команд
- Команды должны иметь тип `request_location_update` или `update_settings`
- Интервалы должны быть в допустимом диапазоне (не больше 1 часа/24 часов)

### 5. Уведомления

#### Права доступа к уведомлениям
- Владелец: полный доступ
- Связанные клиенты: чтение и очистка
- Валидация структуры зашифрованных данных

## Безопасность

### Защита от атак

1. **Защита от повторного использования токена**:
   - Использование Firebase transaction для атомарного обновления `consumed` флага
   - Проверка хеша токена и времени истечения

2. **Ограничение доступа**:
   - Только авторизованные пользователи
   - Проверка принадлежности сервера или связи клиента

3. **Валидация данных**:
   - Проверка структуры команд и уведомлений
   - Ограничение значений параметров

### Ограничения client-only схемы

- Pairing токены имеют ограниченное время жизни (10 минут)
- После истечения токена необходима повторная регистрация сервера
- Для продакшена рекомендуется использовать доверенный бэкенд

## Тестирование

### Сценарии проверки

1. **Владелец сервера**:
   - Регистрация сервера
   - Отправка местоположения
   - Чтение команд

2. **Связанный клиент**:
   - Использование pairing токена
   - Отправка команд
   - Чтение уведомлений и местоположения

3. **Посторонний пользователь**:
   - Должен получить отказ в доступе ко всем данным

4. **Повторное использование токена**:
   - Вторая попытка pairing должна быть отклонена

## Особенности реализации

- Pairing токены генерируются на стороне сервера
- Хеширование токенов происходит с использованием SHA-256
- Для шифрования уведомлений временно используется pairing токен (до реализации доверенного бэкенда)
